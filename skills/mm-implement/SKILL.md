# Implement · 按计划实施

计划是在代码尚不存在时立下的契约。执行计划本质上是一个纪律问题：写代码往往是简单的部分，真正导致失败的是范围蔓延、跳过验证，以及为了迁就代码而临时篡改已定决策。

## 入口检查

先定位仓库根目录（未在 git 仓库中时回退到当前目录），再查找当前计划文件：

```bash
REPO_ROOT=$(git rev-parse --show-toplevel 2>/dev/null || pwd)
find "$REPO_ROOT/.agents/ADR/proposed" -name '*.plan.md' 2>/dev/null | sort
```

- 存在多个计划且用户没有指定执行哪一个 → 询问用户。
- 一个 `.plan.md` 都没有 → 先检查当前对话中是否已有经 `mm-plan` 确认、且按其规则无需落盘 ADR / `.plan.md` 的对话计划：若有，直接按该对话计划的步骤与验证规则执行；若也没有 → 不属于本 skill 的职责：微小的改动直接修改即可，较大的需求应停下并建议用户使用 `mm-plan`。如果用户坚持在没有计划的情况下直接推进，必须明确声明当前工作属于「无计划开发」，并在最终报告中记录这一偏离。

若存在 `.plan.md`，通读该 plan 文件、`.agents/ADR/AGENTS.md`（若存在，重点核对 `## References from code` 规范），以及头部 `ADR:` 与 `Constrained by:` 行指向的所有记录。在此阶段，ADR 记录是只读的：它用于解释约束边界，不授权对决策本身的修改。

当执行开始时，计划里 `ADR:` 与 `Constrained by:` 指向的记录必须已经存在。如果计划里还有一步要求「去创建某份 ADR」，说明规划阶段遗漏了前置决策——立刻停下并建议用户使用 `mm-plan` 补齐。这也是为什么缺失的设计系统必须在规划期补齐，而不是作为交付的第一步临时去搭。

## 进度查询与断点续做

- **仅询问进度时**（如「计划还剩多少未完成」）：只读盘点现状，不修改代码，也不运行带副作用的操作。核对 `## Steps` 中已记录结果的 `Verify:` 行、相关文件状态及 `## Verification` 复选框，直接汇报已完成步骤、待办步骤与待人工核验项后退出。
- **跨会话「继续做」时**：不得仅凭推测跳过前序步骤。结合工作区文件现状（`git status` / 现有代码）与 `## Steps` 中已记录的 `Verify:` 结果定位首个未完成或未验证的步骤，从该步继续；若无法确认某步是否真正跑通，先重跑其 `Verify:` 命令再推进。

## 实施前检查（Preflight）

- 逐项核对 `## Prerequisites`。任何缺失的前置条件必须如实报告为缺失——绝不 mock、绝不静默跳过、绝不「先临时打个桩」。
- 检查工作区（working tree）。如果发现并非由你产生的未提交改动，且即将触及相同文件，先停下来询问用户。

## 推进步骤

按顺序执行各个步骤（如果用户仅指定执行部分步骤，只完成指定子集，并明确说明哪些步骤仍未执行），步骤之间无需逐一请示。仅在验证连续失败、触发停机点（stop point）或现实与 ADR 发生冲突时停下——不要在每一步结束时停下来要许可。

- 每完成一步，立刻执行该步内联的 `Verify:` 命令；绿灯通过后，在 `.plan.md` 对应步骤的 `Verify:` 行旁记入实测结果（如 `— passed, YYYY-MM-DD`；若为对话计划则在汇报中记录），便于跨会话续做与 `mm-land` 核验。没有绿灯通过的步骤不算完成，不得进入下一步。
- 若某步 `Verify:` 失败：允许围绕本步目标做最多 2 次局部修复并重跑验证；若同一错误连续失败、根因超出本步范围，或暴露出前提失效 / ADR 冲突，立刻停下汇报，绝不陷入盲改循环。
- 当某一步标注了 `mm-ui`（`Build`、`Refine` 或 `System`）时，先读取 `skills/mm-ui/SKILL.md` 及对应模式剧本（`references/mode-system.md` / `mode-build.md` / `mode-refine-review.md`），再按其 Read Gate 读取必读透镜文件：
  - 同一视觉交付只需在首次进入 UI 构建前按 `mode-build.md` 格式陈述三行方向（`Visual thesis:` / `Content plan:` / `Interaction thesis:`）并停下等待用户确认，后续 UI 步骤沿用已锁定的方向，再写入包含 9 个固定键名的方向+约束简报注释；
  - Build 必须拆成 **Pass 1**（仅灰度 Token + 骨架/宽度/排版/基线，跑通 `check_ui_rules.py --pass1`）与 **Pass 2**（上色 + 景深 + 收尾/空状态，跑通 `check_ui_rules.py --brief` 及 `check_contrast.py`），禁止一次性生成坍缩；System 步骤须使用 `generate_ramp.py` 生色并跑通 `check_ui_rules.py --tokens`；
  - 产出对照截图（`1440px` + `400px` + 空状态；无浏览器时必须正式列出**逐项未核验项清单**），并在汇报中给出「改动 → `§id`」追溯清单与 5 项 AI Slop Test 逐条 `Clear / Hit` 裁决（可用 `check_ui_rules.py --report` 自检），不要把 `§id` 写满业务代码注释。
- `## Not in scope` 是明确的「禁止事项」清单。即使在范围之外发现了问题，也只需记入最终报告并保持原样；顺手把它们修了，正是两步改动变成无人能读懂的巨大 diff 的原因。
- 需要写注释解释某项长期约束时，在写下对应代码的那一次编辑中同步写好，并严格遵循 `.agents/ADR/AGENTS.md` 中的 `## References from code` 格式：先写清约束后果，再附上 `See ADR <date>-<slug>.`（不得写入公开 API 文档注释）。如果留到最后统一补注释，写出来的往往只有空洞的编号而没有后果说明，还会漏掉真正需要解释的位置。

## 当现实与计划不符时

- 发现 ADR 中的决策不再成立 → 停下，说明原因，并建议用户使用 `mm-plan` 起草替代的新记录。绝不要为了迎合代码去改写原 ADR。
- 某一步的前提条件已失效（文件被移动、依赖已变更、API 与预期不一致） → 停下并汇报。此时要么修订计划，要么调整实现路径；绝不要默默二选一——静默偏离正是计划与代码开始各说各话的起点。
- 触发了计划中的停机点（stop point） → 停下并询问用户。这正是设置停机点的意义。

## 汇报结果

- 已完成的步骤，以及每一步内联 `Verify:` 的真实执行结果。
- 你能够执行的 `## Verification` 检查项及其返回结果。需要人工判断的检查项保持未勾选状态——替人打勾相当于替别人签字验收。
- 发现但有意未修复的问题，并说明理由。
- 后续工作继续推进前，计划本身是否需要修订。

除非用户要求，否则不要执行 `git commit`。不要移动 ADR 记录，不要删除 plan 文件，也不要运行 `mm-land`——将记录升格归档属于用户的验收动作，而不取决于测试是否跑绿。

## 退出条件

满足以下任一情形即可退出：

- **全部完成**：所有步骤均已执行，且每一步的 `Verify:` 结果均已记录（`.plan.md` 中记于对应 `Verify:` 行旁）；`## Verification` 中所有可自动执行的检查项均已运行，并将结果写在了对应复选框旁；ADR 记录仍留在 `proposed/`，plan 文件也依然保留在原位；已明确告知用户哪些项需要人工核验。
- **部分执行或受阻停机**：已明确说明已完成步骤、停止原因（指定子集完成 / Stop point / 前提失效 / ADR 冲突 / 连续验证失败）及仍未完成的步骤，未完成或未通过的检查项保持未勾选。
- **只读进度查询**：已核对并如实汇报当前已完成与待办步骤及人工核验状态，未对工作区做代码修改。
