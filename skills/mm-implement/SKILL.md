# Implement · 按计划实施

计划是在代码尚未落地时立下的契约。执行阶段最容易失控的不是写代码本身，而是范围蔓延、跳过验证，以及为了迁就实现而擅自篡改既定决策。

## 1. 入口检查

定位仓库根目录（非 git 仓库时回退到当前目录），查找待执行计划：

```bash
REPO_ROOT=$(git rev-parse --show-toplevel 2>/dev/null || pwd)
find "$REPO_ROOT/.agents/ADR/proposed" -name '*.plan.md' 2>/dev/null | sort
```

- **存在多个 `.plan.md` 且用户未指定**：询问用户执行哪一份，不要猜测。
- **不存在 `.plan.md`**：检查当前对话是否已有经 `mm-plan` 确认、且按其规则无需落盘的对话计划；若有，直接按其步骤与验证规则执行。若两者皆无，则不属于本 skill 职责——微小修改直接改即可，较大需求应停下并建议先走 `mm-plan`；若用户坚持无计划直接开发，须明确声明处于「无计划开发」状态并在最终报告中记录该偏离。
- **存在 `.plan.md`**：通读计划全篇、`.agents/ADR/AGENTS.md`（若存在，重点核对 `## References from code` 格式），以及计划头部 `ADR:` 和 `Constrained by:` 指向的所有记录。执行阶段 ADR 为只读约束，用于界定边界，不授权推翻决策。

**前置完整性红线**：执行开始时，`ADR:` 与 `Constrained by:` 指向的记录必须已全部存在。若计划里仍有「去创建某份 ADR」的步骤，说明规划阶段漏掉了前置决策（例如缺失的设计系统应先在规划期确立），立即停下并建议通过 `mm-plan` 补齐。

## 2. 进度查询与断点续做

- **仅查询进度**（如「计划还剩多少未完成」）：全程只读，不改代码，不执行带副作用的操作。核对 `## Steps` 中各步 `Verify:` 旁记录的实测结果、相关文件现状及 `## Verification` 复选框，汇报已完成项、待办项与待人工核验项后退出。
- **跨会话「继续做」**：严禁凭印象跳过前序步骤。结合 `git status` / 现有代码与 `## Steps` 中已记录的 `Verify:` 结果定位首个未完成或未验证的步骤；若某步无法确认是否真正通过，先重跑其 `Verify:` 命令再向后推进。

## 3. 实施前检查（Preflight）

- 逐项核对 `## Prerequisites`。任何缺失的密钥、账号、工具或服务必须如实报告为缺失，绝不 mock、静默跳过或临时打桩。
- 检查工作区状态。若发现并非由你产生的未提交改动且即将触及同一批文件，先停下来向用户确认。

## 4. 推进步骤

按顺序执行步骤（若用户仅指定了部分步骤，只完成该子集并明确说明其余未执行步骤），步骤之间无需逐一请示，仅在触发阻塞条件时停下：

### 步骤验证闭环
- 每完成一步，立刻运行该步内联的 `Verify:` 命令。
- 绿灯通过后，将**实测覆盖范围与日期**（如 `scanned 8 .tsx, 1 .css — 0 errors, YYYY-MM-DD`；禁止只写 `passed`）记入 `.plan.md` 对应 `Verify:` 行旁（对话计划则在汇报中记录），方便跨会话续做与 `mm-land` 核验。未通过或实际扫描数为 0 的步骤不算完成，禁止进入下一步。
- **失败重试上限**：若 `Verify:` 失败，围绕当前步骤做最多 2 次局部修复并重跑；若同一错误连续失败、根因超出本步范围，或暴露出前提失效 / ADR 冲突，立即停下汇报，绝不陷入盲改循环。

### 范围与代码注释纪律
- **`## Not in scope` 即禁区**：在范围之外顺手发现的问题只记入最终报告并保持原样，不擅自顺手修改，避免把聚焦的改动膨胀成无法审阅的大 diff。
- **长期约束注释**：写下依赖某项长期约束的代码时，在同一次编辑中按 `.agents/ADR/AGENTS.md` 的 `## References from code` 格式同步落注——先写清违反约束的后果，再附 `See ADR <date>-<slug>.`（不得写入公开 API 文档注释）。

### 涉及 `mm-ui` 的步骤
当某一步标注了 `mm-ui`（`System` / `Build` / `Refine`）时，先加载 [`skills/mm-ui/SKILL.md`](../mm-ui/SKILL.md) 及对应模式剧本，并严格遵循其全部交付门禁：
- **首次方向确认**：同一视觉交付只需在首次进入 UI 构建前，按 `mode-build.md` 声明三行方向（`Visual thesis` / `Content plan` / `Interaction thesis`）并等待用户确认；后续 UI 步骤沿用已锁定方向。
- **逐表面双遍构建**：Build 必须对**每个新增表面/步骤**独立走完 `Pass 1`（灰度骨架 + 空状态结构 + 几何节奏 + `--pass1` 门禁）与 `Pass 2`（色彩 + 景深 + 收尾 + `--brief` / `check_contrast.py`），不得用前一步的 Pass 1 豁免后续侧栏或弹窗；`System` 步骤须程序化生成色板并通过 `--tokens` 与对比度门禁。
- **视觉证据与追溯报告**：按模式要求产出对照截图（无法渲染时须在汇报中逐项列出「未核验项清单」），并在最终交付汇报中提供「改动 → `§id`」追溯与 5 项 AI Slop Test 逐条裁决（不把 `§id` 塞满业务代码注释）。

## 5. 当现实与计划冲突时

- **与已定 ADR 冲突**：若发现 `implemented/` 或已定案核心决策不再成立，停下说明原因，建议用 `mm-plan` 起草替代记录，绝不为迁就代码改写原 ADR。若仅是对仍处于 `proposed/` 的记录在实施中补充局部参数或细节（未推翻主方向），**不得静默改完不报**，须在汇报中单列「提议阶段修订（Pending approval）」说明原因与风险，等待用户确认。
- **前提条件失效**（文件被删改、依赖变更、API 行为与预期不符）：停下并汇报，由用户决定修订计划还是调整路径，绝不静默偏离。
- **触发阻塞确认点（Stop point）**：立即停下并询问用户。

## 6. 汇报结果与收尾边界

向用户汇报：
1. 已完成步骤及每步 `Verify:` 的真实执行结果与覆盖范围。
2. `## Verification` 中可由你执行的检查项及结果；**需要人工判断的验收项保持未勾选**（替人打勾等于替人签字验收）。
3. 发现但按 `## Not in scope` 有意未修复的问题及原因。
4. 继续后续工作前，计划本身是否需要修订。

**红线**：除非用户明确要求，否则不要执行 `git commit`，不要移动 ADR，不要删除 `.plan.md`，也不要调用 `mm-land`——验收归档属于用户的决策动作，不取决于测试是否全绿。

## 7. 退出条件

满足以下任一情形即结束：
- **全部完成**：所有步骤均已执行且 `Verify:` 旁已记录实测结果；`## Verification` 中可自动执行的检查项已运行并记录结果；ADR 仍留在 `proposed/`，`.plan.md` 仍保留在原位；已明确列出待人工核验项。
- **部分执行或受阻停止**：已说明已完成步骤、停止原因（指定子集完成 / Stop point / 前提失效 / ADR 冲突 / 连续验证失败）及剩余步骤，未完成或未通过项保持未勾选。
- **只读进度查询**：已核对并汇报已完成/待办步骤及人工核验状态，未改动工作区代码。
