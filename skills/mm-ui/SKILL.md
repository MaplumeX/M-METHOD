# UI · 界面设计与调优

处理一切带有视觉呈现的工作。四种模式，三项纪律。

不在范围内：后端逻辑、纯文案编辑、用户看不见的底层改动。本 skill 也不是审美生成器——它负责约束与检查，而不是替你凭空编造品味。

## 规划期只读边界

**若当前处于 `mm-plan` 规划期，或用户尚未明确确认方案 / 授权实施，本 skill 全程保持只读（只做项目调研、访谈收敛、方向/Token 方案拟定与命令行对比度校验）**：

- **严禁写入任何文件**：确认前不得写入 `tokens.json`、`tokens.css`、`DESIGN.md`、`preview.html`、业务 UI 代码、约束简报注释、`proposed/design/` ADR 或 `.plan.md`；运行 `scripts/check_contrast.py` 时直接传 `"fg:bg"` 参数校验，不写临时清单文件。
- **落盘时机**：
  - **从 `mm-plan` 转入时**：将设计系统决策草案（含色板、排版/间距/圆角/景深刻度、语义层与对比度校验结果）或 UI 步骤建议交回 `mm-plan` 呈递完整计划；**等用户在 `mm-plan` 中明确确认后**，再按 `mm-plan` 的「确认与流转」规则（含检查 `.agents/ADR/` 是否已初始化）落盘 `proposed/design/` ADR 与 `.plan.md`。
  - **未经 `mm-plan` 直接呼入 `mm-ui` 且尚未授权落盘时**：先完成方案收敛与停机点确认，待用户明确批准后再写入文件。

## Step 0 · 先读项目，再做判断

在提出任何设计结论前先执行这一步。它能避免两个最严重的失误：与项目已有的设计系统打架，或者产出项目根本无法落地的值。

简短汇报以下 5 项：

1. **框架（Framework）** — React / Vue / Svelte / 原生 HTML；SSR 还是 SPA。
2. **现有 Token（Existing tokens）** — CSS 自定义属性、theme 对象、`tokens.json`、`theme/` 目录、Tailwind 配置。
3. **组件库（Component library）** — shadcn/ui、MUI、Ant Design、Chakra、Radix。它们各自带着自己的 token 契约；写组件前先读懂它们。
4. **深色模式（Dark mode）** — 已支持、规划中，还是无。
5. **现有字号与间距刻度（Existing scales）** — 从配置文件中提取真实值，绝不凭记忆瞎猜。

**项目现有系统永远优先。** 如果已有体系，把本 skill 的原则翻译成它的词汇来用；如果还没有，再提出新建方案。绝不直接覆盖、绝不静默迁移、绝不擅自引入没人要求的构建期依赖。

**读完本文件不等于可以动手。** 进入任意模式后，必须先通过该模式的规则必读检查（Read Gate），读取对应的 `references/` 透镜文件再设计或写代码。

## 选择模式

按以下顺序排查，命中第一项即停止：

1. 项目已经有设计系统了吗？没有 → 进入 **System**
2. 正在新增界面内容？ → 进入 **Build**
3. 需要修改现有界面？ → 进入 **Refine**
4. 只需要给意见而不改代码？ → 进入 **Review**

当多种意图混杂时，按 `System → Build → Refine` 的顺序分阶段推进，并明确说出当前处于哪一段。每种模式的**停机点（stop points）**是它们之间唯一的交接边界。

## System · 建立或修改设计系统

**进入时机**：项目尚无设计系统、正在替换旧系统，或缺少某套刻度。

1. **访谈收集**（最多 4 轮，尽量打包提问，允许跳过或采用默认值）：
   - 品牌色、中性色冷暖倾向（冷灰/暖灰）、语义状态色需求（success / warning / error / info）；
   - 产品性格与排版倾向（中性无衬线 / 衬线 / 圆润无衬线、中英文混排与等宽需求）；
   - 形状与景深风格（直角 `0` vs 克制 `4–6px` vs 圆润 `8–12px` 圆角；扁平描边 vs 背景色阶 vs 阴影浮层）；
   - 深色模式与界面密度需求（桌面紧凑型 vs 标准 vs 触控优先）。
2. **构建色板与基础标尺**：
   - 9 阶色板（基准 500 → 900 / 100 → 700 / 300 → 补齐其余色阶；亮度偏离 50% 时提高饱和度）与语义状态色阶；
   - 完整排版（字体栈、11 档字号刻度、主次字重、配套行高与行宽）、间距与控件高度（`32 / 36 / 44px`）、圆角（选定激活档位）、5 档阴影、边框宽度（`1px / 2px`），以及焦点环、`z-index`、动效与断点基础 Token。
3. **建立语义别名层与深色模式映射**：在原始阶梯 Token 之上定义语义 Token（`--surface*`、`--text*`、`--border*`、`--accent*`、`--status-*`、`--disabled-*`），组件只消费语义 Token；若启用深色模式，仅切换语义映射（禁用 `#000` 纯黑，抬升强调色阶并以浅一层表面 + `1px` 边框替代暗底阴影）。
4. **校验对比度**：正文至少 4.5:1、大号文本至少 3:1，亮色与深色模式（若启用）下所有前景色/背景色组合都必须运行 `scripts/check_contrast.py` 检查（基于 skill 所在路径解析，而非项目路径；规划期直接传 `"fg:bg"` 参数校验，不写临时文件），禁止肉眼目测。
5. **产出四份文件（仅在已获授权实施设计系统时执行）**：`tokens.json` / `tokens.css` / `DESIGN.md` / `preview.html`（不预先构建完整业务组件库，完整组件留待 `Build` 按 `10-recipes.md` 实现）。落盘位置优先遵循项目现有样式/主题目录；若项目尚无约定，与用户确认默认目录（如 `design-system/`、`src/styles/` 或项目根目录）。**若处于规划期且尚未获实施授权，只将这 4 份文件的目标路径与 Token/组件契约写入方案草案，不得落盘生成。**
   - `DESIGN.md` 需明确**跨组件通用约定**（激活的圆角档位、卡片层级方式、输入框深度处理、按钮三级样式、焦点/禁用态规则）；
   - `preview.html` 除展示全部 Token 外，还需包含 **4 个金丝雀组件标本**（Button、Form Input、Card、Alert）用于直观验收集成效果。
6. **记录 ADR**：若 `.agents/ADR/` 存在（若不存在且来自 `mm-plan`，交回 `mm-plan` 询问用户是否先运行 `mm-setup`，绝不擅自建半套目录或孤立 `.plan.md`）：
   - **若从 `mm-plan` 规划期转入且尚未授权实施**：**在用户于 `mm-plan` 确认完整方案前不得写盘**；待用户确认后，再仅落盘 `proposed/design/` ADR 与对应的 `.plan.md`（计划交付目标为第 5 步的 4 份文件并跑通 `check_contrast.py`），暂不生成这 4 份实现文件，待独立实施并通过 `mm-land` 升格后再执行业务计划。
   - **若已明确授权落地设计系统**：在停机点确认色板/刻度/命名后，生成上述 4 份文件与 `proposed/design/` ADR；待用户确认 `preview.html` 与对比度检查无误后，提醒通过 `mm-land` 将该 ADR 升格为 `implemented/design/`，避免设计系统已上线而 ADR 长期滞留 `proposed/`。

具体做法见 `11-tokens.md`；若项目使用 Tailwind 或已有组件库，将 `tokens.json` 映射至其主题契约（Tailwind 可参考 `12-tailwind.md`，仅作可选映射）。

**停机点**：色板方向、排版与圆角/景深风格、Token 命名（含语义层），以及**写入任何 ADR / `.plan.md` / 实现文件前的落盘确认**。这些全局契约日后修改代价极高——定稿与写盘前必须先向用户确认（规划期统一交由 `mm-plan` 呈递确认后再落盘）。

**完成标准**：亮/暗模式（若启用）所有对比度组合均经 `scripts/check_contrast.py` 校验通过（exit `0`），且没有任何解释不清用途的色阶或刻度。若处于 `mm-plan` 规划期且尚未获用户确认，完成标准为「设计系统决策草案与验收清单已交回 `mm-plan` 呈递，且工作区零写入」；若已在规划期获用户确认，则 `proposed/design/` ADR 与 `.plan.md` 已落盘；若已授权直接实施，则 4 份文件与 `preview.html` 均通过 `scripts/check_ui_rules.py`（exit `0`）、`preview.html` 的 4 个金丝雀标本已在对应主题下渲染核验（无法渲染须按「视觉证据」声明原因）、`proposed/design/` ADR 已落盘，并已提醒用户验收后走 `mm-land` 升格。

## Build · 新增界面

**进入时机**：新建页面、组件或功能区块。

如果该工作本身需要先做规划（例如新功能、跨多个页面），由 `mm-plan` 负责信息架构与步骤顺序；本模式负责锁定视觉方向与实际落地执行。**若当前尚处于 `mm-plan` 规划期且未获实施授权，只输出方向建议（含主区内容 `max-width` 与密度档位约束）与步骤划分交回 `mm-plan`，禁止提前写入代码或约束简报注释。**

**前置 Read Gate（写简报前必读）**：动手前必须先读取 [02-hierarchy.md](references/02-hierarchy.md)、[03-spacing.md](references/03-spacing.md)、[04-typography.md](references/04-typography.md)、[06-depth.md](references/06-depth.md)、[10-recipes.md](references/10-recipes.md) 与 [15-direction.md](references/15-direction.md)（涉及图片或收尾装饰时补读 [07-images.md](references/07-images.md)、[08-finishing.md](references/08-finishing.md)）。禁止仅凭 `SKILL.md` 概览直接写界面。

**顺序就是方法本身。** 搞乱顺序就会做出过度装饰、结构松散的界面。

0. **锁定方向（Lock the direction）**（见 `15-direction.md`）。用具体的词汇命名美学风格并确定一个标志性特征——「简洁现代（clean and modern）」不是方向。在写任何标记语言前，先用三行分别陈述视觉主题（visual thesis）、内容规划（content plan）和交互假设（interaction thesis）。
1. 从具体功能入手，而不是先搭空壳（shell）。`§1.1`
2. 先用纯灰度工作——逼迫间距、字号和明暗对比来承担视觉层级。`§1.2.1`
3. 对内容进行优先级分级（主 / 次 / 辅），并对操作进行分级（1 个主操作 / 少量次操作 / 若干弱操作）。`§2.1 §2.8`
4. 严格从预设刻度中取用间距与字号布局。`§3.2 §4.1`
5. 设定画布上限、行宽与阅读节奏：约束内容宽度，每行 45–75 个字符，行高随行宽与字号匹配。`§3.3 §4.3 §4.5`
6. 然后再上色，再加景深（阴影/层级），最后做收尾细节——严格按此顺序。`§5 §6 §8`
7. 空状态属于功能本身的一部分，与主功能同步设计。`§8.4`

常见组件直接查阅 `10-recipes.md`，不要每次重新发明。

**两阶段写入纪律（禁止一次性坍缩）**：即使项目已有设计系统 Token，也必须拆成两步写入（先写结构与灰度，再叠加色彩与景深）：
- **Pass 1（骨架 + 灰度 + 几何节奏）**：仅使用中性灰阶 Token（`--surface*`、`--text*`、`--border*`）完成布局容器、`max-width`、字号/行高/行宽、组内外间距与基线对齐；禁止写入 `--accent*`、`--status-*` 与装饰性 `box-shadow`。先确认纯灰度下层级已独立成立（`§1.2.1`）。
- **Pass 2（上色 + 景深 + 收尾 + 空状态）**：在 Pass 1 之上按 `§5` → `§6` → `§8` 依次叠加品牌/语义色、输入框 inset / 浮层阴影与空状态细节。

**在写下第一行标记语言之前**，先在目标文件顶部以注释形式写一份结构化**约束简报（constraint brief）**（汇报完成后若需保持业务代码整洁，可保留核心几何契约注释或按 `mm-implement` 规范将 `§id` 追溯留在汇报中）。简报必须包含以下 6 项，缺一不可：

1. `Rules read:` 本次实际读取的参考文件与摘取的核心数值。
2. **画布与行宽上限（`§3.3 / §4.3`）**：主内容区 `max-width`（全宽表格/画布须写明 `§3.3.3` 理由）+ 正文 `measure`（`45–75ch` / `20–35em`）。
3. **字号与行高映射（`§4.1 / §4.5`）**：各级字号与配套 `line-height`（如标题 `1.0–1.25`、正文随行宽 `1.5–1.75`；禁止全站单一 `1.5`）。
4. **密度档位与间距差（`§3.1.2 / §3.6`）**：声明密度档位（紧凑 / 标准 / 宽松），以及具体的「组内间距 vs 组间间距」阶梯值。
5. **对齐与景深契约（`§4.4 / §6.1.3 / §6.2.a`）**：文字行对齐方式（`baseline`；纯图标或单行等高控件另标豁免理由）+ 输入框 inset / 浮层阴影档位。
6. **内容分级、主操作与空状态（`§2.1 / §2.8 / §8.4`）**：主/次/辅内容、唯一主操作、空状态容器定位/图形/CTA 及要隐藏的无用支持控件。

**停机点**：设计方向（不是抠细节）、缺少基础刻度（转回 System）。

**完成标准**（必须全部满足，不接受「视觉协调」等主观描述）：
1. 6 项约束简报完整且在写代码前已通过前置 Read Gate；
2. `scripts/check_ui_rules.py <样式或源码目录>`（以及新增或调整配色组合时的 `scripts/check_contrast.py`）全部返回 exit `0`；
3. 已产出**对照截图**（`1440px` 宽屏 vs `400px` 窄屏 + 空状态；有 `preview.html` 或同代页面时并排核对，新页须含 Pass 1 灰度对照），并按 `09-antipatterns.md` 完成反证排查（环境无法渲染时按「视觉证据」声明原因与未核验项）；
4. 交付汇报中包含「组件/改动 → 规则编号 `§id`」追溯清单；
5. `15-direction.md` AI Slop Test 五项反射模式逐条给出 `Clear` 或 `Hit → 已修复（说明）` 裁决。

## Refine · 调整现有界面

**进入时机**：「感觉有点怪」「让它更好看点」、清理设计债务。**若当前尚处于 `mm-plan` 规划期且未获实施授权，只做只读诊断并输出按透镜拆分的整改步骤交回 `mm-plan`，禁止在确认前修改代码。**

1. 先截图：同时截取桌面端和移动端宽度。
2. 先查 `09-antipatterns.md`——如果症状已经在列表中，你直接拿到了规则编号。否则按顺序扫一遍以下七个诊断透镜，并在**第一个能解释当前抱怨的透镜处停下**；后面的维度往往只是它的连带后果。

   | # | 诊断透镜 | 参考文件 |
   |---|---|---|
   | 1 | 视觉层级（Hierarchy） | `02-hierarchy.md` |
   | 2 | 布局与间距（Layout and spacing） | `03-spacing.md` |
   | 3 | 排版（Typography） | `04-typography.md` |
   | 4 | 色彩（Color） | `05-color.md` |
   | 5 | 景深（Depth） | `06-depth.md` |
   | 6 | 图片与图形（Images） | `07-images.md` |
   | 7 | 收尾细节（Finishing） | `08-finishing.md` |

3. **每次只改一个透镜** → 重新截图 → 对比效果 → 再进下一个。调整间距时就只调间距。
4. 以可审阅的 diff 提交结果，每处改动附上对应的规则编号。

**停机点**：缺少必要的 Token（转去 System）、整体方向错了（退回 Build）。

**完成标准**：存在修改前后的对比截图（若环境无法渲染，须按下方「视觉证据」一节说明原因与未核验项）、`scripts/check_ui_rules.py`（以及触及配色时的 `scripts/check_contrast.py`）返回 exit `0`，且每处修改都能追溯到具体的规则编号。

## Review · 只评审不改代码

**进入时机**：「帮忙看看」「这里有什么问题」、上线前检查，或用户贴了一张截图。

流程与 Refine 的第 1–2 步相同，但不修改任何代码。

**产出**一份问题报告：**症状 → 规则编号 → 具体修复建议**，按严重程度排序，而不是按透镜顺序罗列。同时运行 `15-direction.md` 中的 AI Slop Test：一份连「这是三张毫无区分度的同款卡片」都漏掉的评审报告，检查的只是合规性，而不是设计本身。

**完成标准**：每条发现都带有规则编号，并且明确声明哪些部分没有检查。没有规则编号的发现只是个人意见——而「觉得不对劲」的个人意见，用户在找你之前就已经有了。

## 三项纪律

**1. 每次只改一个透镜。** UI 调整中最大的陷阱就是把间距、字重、阴影全改了一遍，然后得出结论「整体看起来更好了」。下一次某个地方崩掉时，你根本分不清是哪一处改动引起的。只改一个维度，看效果，然后再改下一个。

**2. 事实证据先于修改意见。** 先说出截图里客观存在什么——当前用到了几档间距、哪些元素在重复、对比度具体是多少——然后再说应该改什么。不带证据的「多留点白」只是噪音，谁也不知道该改哪里。

**3. 规则编号是唯一可讨论的最小单元。** 「这里感觉太挤了」没法讨论；「违反 `§3.6`：组间距等于组内间距」可以明确讨论和验证。每一条评审发现与每一处改动都必须携带规则编号。

## 视觉证据

**不看渲染效果不做视觉结论，不看对照物不作质量判定。** 只要环境允许（本地开发服务 + 截图），就必须实际渲染并查看截图。光读标记语言和 CSS 能发现间距与结构问题，但发现不了「阴影看起来很脏」或「视觉层级没立起来」；只看单张正常态截图，又很容易把“Token 一致、没报错”误判成“好看”。

- **Build 模式对照矩阵**：必须同时查看 **1440px 宽屏**（专门暴露 `§3.3 / §4.3` 画布无约束、空状态贴边）、**400px 窄屏**（专门暴露换行与控件挤压）以及 **空状态** 截图；有 `preview.html` 或同代页面时并排对照，新页面须对比 Pass 1 纯灰度与 Pass 2 完成态，并拿 `09-antipatterns.md` 逐条反证排查，而非凭感觉判定「协调」。
- **Refine 模式对照**：必须保留修改前后的桌面端与移动端对比截图。

如果确实无法渲染（无浏览器环境、无网络、仅改动基础库），必须在报告中明确说明，并标出哪些结论未经视觉核验。

## 决策记录化

生命周期超过单个页面的 UI 决策应沉淀为 ADR，而不是留在代码注释里：

| 决策类型 | 存放位置 |
|---|---|
| 色板与语义 Token、排版与间距刻度、圆角/阴影及跨组件基础契约 | `proposed/design/` |
| 组件库或设计系统选型 | `proposed/design/` |
| 深色模式策略 | `proposed/design/` |
| 单个页面的局部布局权衡 | 不写 ADR——留在 plan 文件中 |

撰写记录时遵循 `.agents/ADR/AGENTS.md`（若在 `mm-plan` 规划期产生，须待用户确认完整方案后再统一落盘，不得在确认前提前写入）。单个页面的样式微调不值得立档，它所依托的设计系统规范才值得记录。
