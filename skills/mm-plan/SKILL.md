# Plan · 规划

计划不是你单方面产出的文档，而是你与用户共同敲定的一棵决策树：每个决策都会分叉出依赖它的子决策，直到没有任何分支被静默假设为止，规划才算完成。

## 先过准入闸门

在提出任何问题之前，先判断属于哪条出口：

- **不属于规划（Not my job）**：Bug 报告、堆栈报错、偶发失败的测试、以及「为什么这里坏了」属于问题诊断，不是规划。用一句话说明并转出。建立在未诊断 Bug 之上的计划，只是走了更多步骤的猜测。
- **评估模式（Evaluation）**：用户询问「值不值得做」「该不该保留」「要不要构建」某单一目标。不直接出实现计划，按 `references/modes.md` 中的 Evaluation 结构给出裁决、翻转条件与最低成本验证。
- **分诊模式（Triage）**：输入是一组彼此独立、可分别取舍的需求、截图或问题清单。按 `references/modes.md` 中的 Triage 表格逐项裁决并排序，不合并条目。
- **轻量模式（Lightweight）**：问题已明确，唯一的开放问题是「怎么改」，且不存在真正有分歧的备选方案。先用一句话点出最直接的粗暴做法，再用 2–3 句话说明改动内容、改动位置及原因，然后等待确认。
- **完整模式（Full）**：其余所有情况。按以下流程推进。

如果在轻量模式下发现了三种及以上本质不同的方案且各有明显权衡，应立即升级为完整模式。以上各变体的格式与退出条件详见 `references/modes.md`。

## 夯实事实基础

在提出任何建议前，先读取以下内容：

- 根目录 `AGENTS.md`，以及仅与当前问题匹配的领域规则。把整棵规则树全量加载会稀释真正起约束作用的规则。
- `.agents/ADR/AGENTS.md`、覆盖当前区域的 `implemented/` 记录、任何存在重叠的 `proposed/` 记录，以及同主题的 `rejected/` 记录（避免重复探讨或重演已被否决的方案）。如果新计划与某个待推进提案重复，必须明确它是该提案的延续还是替代。若仓库尚未建立 `.agents/ADR/`，则跳过此项：本 skill 必须能在 `mm-setup` 运行前正常工作。
- 当计划涉及默认配置、端口、环境变量或启动参数时，读取真实的配置文件。直接引用现场真实值，绝不凭记忆背诵。

如果正在成形的计划与已有文档规则或 ADR 冲突（例如「禁止 X」或「必须 Y」），必须明确指出冲突的是哪条规则、哪个步骤，以及你的建议。不要静默绕过，也不要直接卡死——应该在用户还有选择余地时把冲突摆到台面上。若计划将替代某份 ADR，需产出一份新记录指向旧记录，并在后续 `mm-land` 升格新记录时补全旧记录指向新记录的反向链接；绝不要把旧决策原地改写成另一个意思。

## 事实归你查，决策归用户

尽可能自己查清所有客观事实：框架内置能力、官方推荐模式、生态标准、当前文件内容、现有依赖是否已自带解法。除非你能说清在当前具体场景下它为何不够用，否则已有的官方方案就是默认推荐。

对于需要跨多个文件检索或查阅外部最新文档的调研，派发子 agent 去查，不要用宝贵的规划上下文来堆搜索细节。绝不要向用户询问你自己就能查到的事实。也不要因为等待某个调研而阻塞整轮提问——只有依赖该事实的下游问题需要等待，其余边界上的问题立刻在本轮提出。

决策权属于用户。把每个待决事项连同你的推荐选项一并交给用户，然后等待回答。

## 逐轮推进

按轮次推进决策树。**当前边界（frontier）**是指所有前置条件都已敲定、现在无需猜测未回答问题即可直接发问的所有决策点。在一轮中一次性抛出整个边界上的所有问题，然后停下来等待。

```
❓ **Q1** — **<问题标题>**

<一句话背景说明>

- **A.** <选项> — <代价或收益>
- **B.** <选项> — <代价或收益>

➡️ **A**，因为 <理由>。

---

❓ **Q2** — **<问题标题>**

<背景说明；无选项——答案是关于意图或事实的确认，而非设计二选一>

➡️ <你的推荐答案>
```

只要设计空间里确实存在多个选项，就明确列出来：列出选项能降低用户的回答成本，也能体现你考虑过哪些路径。每个选项都要写出它的**后果**，而不只是一个名字——用户是在为后果做选择，不是在选标签。如果答案只是一个意图、一个数值或一个客观约束，则省略选项列表。

绝不要只给出一组等价选项却不做推荐。甩出一份没有倾向的菜单是在逃避决策，把工作原封不动退回给用户而没有替他缩小范围。

每个问题的措辞应保证用户回答「是 / 同意」即代表采纳你的推荐方案。如果某个问题依赖本轮中尚未敲定的另一个问题，它属于下一轮，不要放在本轮。

每一轮都会重塑决策树：已敲定的决策会把边界向外推进，解锁原本依赖它的后续问题。重新计算边界，发出下一轮问题。

如果一开始就存在两条及以上本质不同的架构或设计形态，且各自会引出完全不同的下游子问题，应在决策树的最早轮次就将其作为根节点边界问题对比并拍板——不要先沿着其中一条路线问完几轮细节，最后才推翻重选。

在推进过程中持续记录已敲定的决策以及沿途被否决的选项——被否决的选项正是后续 `## Alternatives considered` 的素材来源。

轮次没有上限。由决策树本身的复杂度决定需要几轮，而不是凭感觉认为「三轮就够了」。如果一轮里只问了一个问题，通常说明边界计算有误：彼此独立的问题应当合并在同一轮里。

如果用户对某个边界问题表示「不知道」，那它通常不是一个设计决策：要么是需要你去查证的事实，要么是需要显式声明的假设约束（例如「暂且假设 X，这意味着 Y」）。绝不要让一个未回答的问题悄悄变成默认前提。

## 收口自检

所有分支已敲定。在输出计划前，在内部静默过一遍以下约束（**不要把检查清单打印出来**；只有未通过时才修改方案或退回上一阶段）：

- **假设与压测**：若涉及外部依赖、高并发或数据迁移，运行 `references/modes.md` 中的 Attack angles 检查。若核心假设被击穿，或突然发现漏掉的关键分支，退回「逐轮推进」重新确认或直接说明为何舍弃原方案，不在结尾硬圆。
- **简洁性与零配置**：每一个 `try/catch`、重试、降级和开关标志都必须对应明确的失败模式；若计划大部分都在围绕异常依赖打补丁，应直接替换路径。默认优先零配置和复用现有代码，只有在证明零配置无法胜任时才引入新安装项、环境变量或服务。
- **可执行性与阶段独立**：禁止出现 `TBD`、`TODO`、「同第 N 步」或「Phase 0：调研」；若拆分为多阶段，每一阶段都必须能独立使用，否则合并为一个阶段。
- **半径与回退**：涉及超过约 8 个文件，或包含迁移、发布、外发消息等外部状态变更时，必须在计划中显式写出 `Rollback` 与 `Stop points`。

## 交付计划

先在对话中用以下结构呈现完整的执行计划，供用户一次性审阅（无内容的可选槽位直接省略，不要写 `None.`）：

- **Scope & Not in scope** — 一两句话概括要做什么、建立在哪些现有代码之上，以及明确不做什么（有意延后的事项连同原因与负责人一并写入 `Not in scope`，模糊缺口不允许留在这里）。
- **Key decisions** — 3–5 条本次敲定的核心决策，附带推理与沿途实际讨论过但被否决的选项。
- **Steps** — 按顺序列出每一步触及的文件/改动，以及一条可执行的内联验证（`Verify:`）。涉及视觉界面时：加载 `mm-ui/SKILL.md` 及对应模式剧本（`references/mode-system.md` / `mode-build.md` / `mode-refine-review.md`）；已有设计系统则在对应步骤标明 `mm-ui` 模式（`Build`、`Refine`），并在 `Verify:` 中纳入静态门禁（`check_ui_rules.py --pass1` / `--brief` / `check_contrast.py`）；若步骤涉及双栏/侧边栏+自适应主区布局，计划中必须同时写明主区内容 `max-width` 上限（或明确全宽理由，防止把无约束画布写死成规格），具体视觉方向留到 `mm-ui` 实施前锁定；尚无设计系统则先通过 `mm-ui` 的 `System` 阶段（仅做调研访谈与方案收敛，不写入任何文件，色板须按 `§5.3` / `generate_ramp.py` 推导而非手挑 hex）确立设计系统决策草案，随计划一并呈递等待用户确认——确认后再按下方「确认与流转」落盘为独立的 `proposed/design/` ADR 与 `.plan.md`（计划 `Verify:` 须包含 `check_contrast.py` 与 `check_ui_rules.py --tokens`，先独立实施并经 `mm-land` 升格，或作为独立前置交付），并由业务计划以 `Constrained by:` 引用；绝不要在用户确认前提前写入 ADR、`.plan.md` 或 token 实现文件，也不要把建设计系统塞成业务计划的 Step 1。
- **Verification** — 整体交付的验收清单（最终自动检查命令 + 需人工确认的行为）。
- **Prerequisites**（按需）— 所需 API Key、账号、工具或服务及用途；未核实的前置条件归入此项，不要写成已验证。
- **Rollback / Stop points**（按需）— 外部状态的回退路径（或明确标注不可逆），以及最容易踩坑、必须停下来询问用户的断点。

## 确认与流转

呈递上述计划后等待用户表态。**用户确认前不要提前写入任何 ADR、`.plan.md` 或实现文件（包括进入 `mm-ui` 后产生的设计系统 ADR 与 token/preview 文件）**（除非用户在规划开始前已明确授权直接动手）。

根据用户回复与决策性质自然分流：

1. **用户仅确认方案（「可以」「行」「looks good」）**
   - **不涉及长期影响力决策**（变更可轻易逆转）：无需写 ADR，也不要创建无 `ADR:` 头的孤立 `.plan.md`。对话计划即为最终定稿，等待下一步指示。
   - **涉及长期影响力决策，且仓库已初始化 `.agents/ADR/`**：此时先确保目标分类目录存在（`mkdir -p .agents/ADR/proposed/{class}`），再落盘以下两份文件，向用户汇报路径与 `## Verification` 清单后**结束规划**（留待用户后续下令或在新会话用 `mm-implement` 执行；绝不提前写入 `implemented/`）：
     - `.agents/ADR/proposed/{class}/yyyy-mm-dd-<slug>.md` — 每个决策一份记录，格式遵循 `.agents/ADR/AGENTS.md`（`design` 类涵盖色板、字号间距、圆角阴影与组件契约；单页具体布局留在 plan 文件即可）。
     - `.agents/ADR/proposed/{class}/yyyy-mm-dd-<delivery-slug>.plan.md` — 执行附件，格式遵循 `references/plan-file.md`；只写 `Scope / Not in scope / Steps / Verification` 及按需槽位，不重复抄写决策理由。
   - **涉及长期影响力决策，但仓库尚未初始化 `.agents/ADR/`**：询问用户是否先运行 `mm-setup` 初始化后再落盘；若用户选择不启用 ADR，以当前对话中的计划为准，不创建半套目录或孤立 `.plan.md`。
   - **交接退出（Handoff）**：若用户要求交接单或当前环境无法继续推进，按上述规则直接落盘（或无 ADR 库时直接确认对话中的完整计划），不空谈受阻原因。

2. **用户直接授权实施（「开工」「按这个做」「implement it」）**
   - 视为同时确认方案并授权执行。若本次需落盘 ADR 且仓库已启用 `.agents/ADR/`，先写好上述 ADR 与 `.plan.md` 并声明正在执行哪份 plan，再读取 `mm-implement` 开始实施（轻量模式或无需落盘的改动可直接动手，无需强走 `mm-implement`）。
   - 在用户明确要求实施之前，不要读取 `mm-implement`，也不要编写任何代码。

3. **规划前已明确授权直接实施（「直接做」「别问了」）**
   - 查清事实并完成「收口自检」后，直接按第 2 条路径推进：必要时先写好 ADR 与 `.plan.md`，随即开始实施。
