# Plan · 决策树规划

计划不是单方面写出的文档，而是与用户共同敲定的一棵决策树：每一条分支都要被显式确认，直到不存在任何静默假设为止。

## 1. 准入闸门

在发问前，先判定当前请求对应的出口（详见 [`references/modes.md`](references/modes.md)）：

- **职责外（Routing out）**：Bug 报告、堆栈报错、偶发失败测试、性能回归诊断、或无行为疑问的纯重构。用一句话点明性质并停止——基于未诊断缺陷做的计划只是二次猜测。
- **评估模式（Evaluation）**：询问「值不值得做 / 该不该保留 / 要不要建」单一目标。按 `modes.md` 的 Evaluation 结构给出裁决、翻转条件与最低成本验证，不直接出实现计划。
- **分诊模式（Triage）**：输入是一组彼此独立的需求、截图或问题清单。按 `modes.md` 的 Triage 表格逐项裁决并排序，不合并条目。
- **轻量模式（Lightweight）**：问题明确，唯一开放问题是「怎么改」，且不存在真正有分歧的备选方案。先用一句话点出最直接的粗暴做法，再用 2–3 句话说明改动内容、位置与原因，然后等待确认。若过程中发现 3 种及以上本质不同且各有权衡的方案，立即升级为完整模式。
- **完整模式（Full）**：其余所有情况，按以下流程推进。

## 2. 夯实事实基础

提出任何建议前，先完成以下只读核查：

- **项目规范**：读取根目录 `AGENTS.md`，以及仅与当前问题匹配的领域规则（避免全量加载无关规则树，稀释约束力）。
- **既有决策**（若 `.agents/ADR/` 存在；尚未运行 `mm-setup` 时跳过此项）：读取 `.agents/ADR/AGENTS.md`、覆盖当前区域的 `implemented/` 记录、存在重叠的 `proposed/` 记录（明确本计划是其延续还是替代），以及同主题的 `rejected/` 记录（避免重演已否决方案）。
- **现场配置**：涉及默认配置、端口、环境变量或启动参数时，必须读取真实配置文件并引用现场真实值，严禁凭记忆作答。

**冲突处理**：若成形中的方案与已有规则或 ADR 冲突，必须当场点明冲突条款与建议路径，绝不静默绕过，也不直接卡死。若计划替代某份旧 ADR，须产出一份新记录指向旧记录，并在后续 `mm-land` 升格时补全旧记录指向新记录的反向链接；严禁原地篡改旧决策语义。

## 3. 事实自查与权责边界

- **客观事实由你查清**：框架内置能力、官方模式、生态标准、现有代码与依赖是否自带解法，全部自行核实。除非能说清在当前场景下为何不够用，否则已有官方/内置方案即为默认推荐。绝不向用户索要你自己能查到的事实。
- **复杂调研外包**：需要跨多文件检索或查阅外部最新文档时，派发子 agent 调研，避免搜索细节挤占主规划上下文。等待调研时不要阻塞同一轮里彼此独立的边界问题。
- **决策权归用户**：将每个待决事项连同你的推荐项一并交由用户拍板，然后等待回复。

## 4. 逐轮推进决策树

按轮次向外推进。**当前边界（frontier）**指所有前置依赖均已敲定、无需猜测即可发问的决策集合。每轮一次性抛出当前边界上的全部问题，随后停下等待：

```markdown
❓ **Q1** — **<问题标题>**

<一句话背景说明>

- **A.** <选项> — <代价或收益>
- **B.** <选项> — <代价或收益>

➡️ **A**，因为 <理由>。

---

❓ **Q2** — **<问题标题>**

<背景说明；答案是意图、数值或客观约束时省略选项列表>

➡️ <推荐答案>
```

发问纪律：
- **写清后果**：存在多个设计方向时列出选项及各自后果（用户是在为代价/收益做选择，不是选标签）；意图或客观数值类问题省略选项。
- **必须表态**：绝不甩出无倾向的等价选项菜单。措辞应确保用户回复「是 / 同意」即可直接采纳推荐方案。
- **严控依赖**：依赖本轮未决问题的问题留到下一轮。若存在两条及以上会引出完全不同下游子树的顶层架构路线，必须在最早轮次作为根节点拍板，绝不在问完几轮细节后再推翻重选。
- **收集否决项**：随手记录沿途排除的选项及理由，作为后续 `## Alternatives considered` 的素材。
- **轮次不设固定上限**：由决策树复杂度决定轮数。若一轮只问了一个问题，通常说明边界计算漏掉了可并行的独立问题。
- **处理「不知道」**：用户表示「不知道」时，它通常要么是待查证的事实，要么是需要显式声明的假设（如「暂且假设 X，这意味着 Y」），绝不让未决问题静默变成默认前提。

## 5. 收口自检（内部静默执行，勿打印清单）

所有分支敲定后、输出完整计划前，在内部逐项过检；仅在未通过时修正方案或退回上一阶段：

- **假设压测**：涉及外部依赖、高并发或数据迁移时，运行 [`references/modes.md`](references/modes.md) 中的 Attack angles。若核心假设被击穿或漏掉关键分支，退回第 4 步重新确认或说明舍弃理由，不在结尾强行自圆其说。
- **简洁与零配置**：每个 `try/catch`、重试、降级与开关标志都须对应明确失败模式；若方案主体都在为异常依赖打补丁，直接换路径。默认零配置并复用现有代码，确证不足时才引入新依赖、环境变量或服务。
- **可执行性与有效验证**：禁止出现 `TBD`、`TODO`、「同第 N 步」或「Phase 0：调研」。拆分多阶段时，每一阶段都必须能独立交付使用，否则合并。每一步的 `Verify:` 命令必须匹配该步实际产出的文件类型且**有能力失败**（禁止将只扫 `.css` 的检查挂在 `.tsx` 步骤上，也不允许把“扫描 0 个文件退出 0”算作验证通过）。
- **变更半径与回退**：触及超过约 8 个文件，或包含迁移、发布、外发消息等外部状态变更时，必须显式写出 `Rollback` 与 `Stop points`。

## 6. 交付计划

在对话中呈递完整计划供用户审阅（空可选槽位直接省略，不要写 `None.`）：

- **Scope & Not in scope**：概括改动范围、依托的现有代码，以及明确不做什么（有意延后的事项须连同原因与负责人一并写入 `Not in scope`，不留模糊缺口）。
- **Key decisions**：3–5 条本次敲定的核心决策，附推理与实际讨论过并否决的备选方案。
- **Steps**：按顺序列出每一步触及的文件/改动，以及一条可执行的 `Verify:` 命令。
- **Verification**：整体交付验收清单（最终自动检查命令 + 需人工确认的行为）。
- **Prerequisites**（按需）：所需 API Key、账号、工具或服务及用途；未核实的前置条件归入此处，不写成已验证。
- **Rollback / Stop points**（按需）：外部状态回退路径（或明确声明不可逆），以及最容易出错、必须停下来询问用户的确认断点。

### 涉及视觉界面时的专项约束

若计划包含 UI 设计或前端视觉改动，加载 [`skills/mm-ui/SKILL.md`](../mm-ui/SKILL.md) 及对应模式剧本，并严格遵守其**规划期只读边界**（确认前**禁止写入任何文件**）：

- **尚无设计系统**：先经 `mm-ui` 的 `System` 模式完成只读调研与方案收敛，随本计划一并呈递设计系统决策草案（色板须按程序推导并完成内联对比度校验）。用户确认后，落盘为独立的 `proposed/design/` ADR 与 `.plan.md`（先独立实施并通过 `mm-land` 升格，或作为独立前置交付），由业务计划通过 `Constrained by:` 引用——绝不把建设计系统塞进业务计划的 Step 1。
- **已有设计系统**：在对应 UI 步骤标明 `mm-ui` 模式（`Build` / `Refine`），并将 `mm-ui` 静态门禁纳入该步 `Verify:`；若步骤涉及「侧边栏 + 自适应主区」双栏布局，计划中必须写出主区 `max-width` 上限（或明确全宽理由），具体视觉方向留待 `mm-ui` 实施前锁定。

## 7. 确认与流转

呈递计划后等待用户表态。除非用户在规划开始前已明确授权「直接做」，**用户确认前严禁写入任何 ADR、`.plan.md`、token/preview 或业务实现文件**：

1. **仅确认方案（「可以」「行」「looks good」）**
   - **可轻易逆转的小改动**（不涉及长期架构/设计决策）：无需建 ADR，也不得创建无 `ADR:` 头的孤立 `.plan.md`。对话计划即为最终定稿，等待下一步指令。
   - **涉及长期决策且已启用 `.agents/ADR/`**：确保目标分类目录存在（`mkdir -p .agents/ADR/proposed/{class}`），写入以下两份文件，向用户汇报路径与 `## Verification` 清单后**结束规划**（绝不提前写入 `implemented/`）：
     - `.agents/ADR/proposed/{class}/yyyy-mm-dd-<slug>.md` — 每个决策一份，遵循 `.agents/ADR/AGENTS.md`（`design` 类涵盖色板、字号间距、圆角阴影与组件契约；单页局部布局留在 plan 文件）。
     - `.agents/ADR/proposed/{class}/yyyy-mm-dd-<delivery-slug>.plan.md` — 执行附件，遵循 [`references/plan-file.md`](references/plan-file.md)；只写执行步骤与验收，不重复抄写决策理由。
   - **涉及长期决策但尚未初始化 `.agents/ADR/`**：询问是否先运行 `mm-setup`；若用户选择不启用 ADR，以对话计划为准，不创建半套目录或孤立 `.plan.md`。
   - **交接退出（Handoff）**：若用户需要交接或当前环境受阻无法继续，按上述规则直接落盘（无 ADR 库时确认对话计划），不空谈受阻原因。

2. **确认并直接授权实施（「开工」「按这个做」「implement it」）**
   - 需落盘 ADR 且仓库已启用 `.agents/ADR/` 时，先按第 1 条落盘 ADR 与 `.plan.md` 并声明即将执行的 plan，再读取 `mm-implement` 开始实施（轻量模式或无需落盘的改动可直接动手）。
   - 在用户明确授权实施前，不读取 `mm-implement`，也不编写任何代码。

3. **规划前已明确授权直接实施（「直接做」「别问了」）**
   - 查清事实并完成第 5 步收口自检后，直接按第 2 条路径推进。
